# Data Lifecycle

This document maps a patient record from intake to deletion. It complements
[`PRIVACY-DATA-HANDLING.md`](PRIVACY-DATA-HANDLING.md) and the operational
[`PRODUCTION-CHECKLIST.md`](PRODUCTION-CHECKLIST.md).

## 1. Intake

1. Patient data is created by resepsionis/perawat or the seed script (dev/test only).
2. `nikEncrypted`, `phoneEncrypted` use AES-256-GCM; `nikHash` supports dedup; `nikMasked` is the
   safe display value. Never store plaintext NIK/phone.
3. `Patient.consentStatus` starts as `PENDING`. Outbound contact is not allowed until `GRANTED`.

## 2. Consent state machine

```text
PENDING --grant--> GRANTED --revoke--> REVOKED
   |
   +-- refuse --> REVOKED   (no REFUSED state; no outbound, record still available to authorized staff)
```

- `consentAt` / `consentRevokedAt` record timestamps; a grant after revocation sets a new `consentAt`,
  clears `consentRevokedAt`, and reopens outbound processing.
- Withdrawal is enforced at the point of the real provider call: `agents/urgentCaller.ts` reloads
  the patient and requires `consentStatus === GRANTED`; pending queued work therefore cannot deliver
  after revocation. Approval tokens are one-use (`ApprovalUse`) and expiry-checked.
- Withdrawal creates a `CONSENT_WITHDRAWAL` DSR ticket stamped with the 3×24 h SLA.

## 3. Clinical use & retention

- `retentionUntil = last Visit.visitDate + 25 years` (see `lib/privacy.ts`). `npm run retention:sweep`
  recomputes it for all active patients weekly and escalates overdue DSR tickets. Visit, triage, lab, prescription, and medical record rows are linked to the patient and visit.
- `retentionUntil` is the per-patient deadline; if unset, the clinic-wide policy applies.
- `Report.sentAt` and `Report.expiresAt` control generated report delivery and file purge.
- API/agent logs follow their own retention settings; signed audit rows are append-only in routine
  production (destructive dev/test seed excepted).

## 4. Deletion / anonymization

```text
deletion request -> deletionRequestedAt + deletionReason
                 -> retain (legal hold) OR deletedAt (soft delete)
                 -> anonymizedAt when identifiers are irreversibly replaced
```

- Hard deletion of audit logs is not allowed in routine production retention; keep the decision and
  actor in the audit trail. The destructive dev/test seed is the documented exception (see §5).
- When statutory medical retention is still active, anonymize identifiers and keep clinical facts.
- Backups are immutable until retention expires; a deletion is fully effective only after every
  affected backup ages out. Record that fact in the deletion ticket.

## 5. Seed & schema safety

- `prisma/seed.ts` deletes all tables. It calls `assertDestructiveSeedAllowed()` and requires
  `NODE_ENV=development|test` plus `ALLOW_DESTRUCTIVE_SEED=1`. Production always throws.
- Seed passwords come from `SEED_ADMIN_PASSWORD`; if missing locally, a random password is printed
  once. There is no hardcoded demo password in source.
- Initial migrations exist for SQLite (`prisma/migrations`) and PostgreSQL
  (`prisma/migrations-postgres`). The PostgreSQL schema is generated by
  `node scripts/sync-postgres-schema.mjs`; deploy it with
  `npx prisma migrate deploy --config prisma/postgres.config.ts`.
- Existing databases created with `db push` should keep using `db push` or be baselined; do not run
  the initial migration on a populated database without a migration baseline.

## 6. Backup & restore

- `npm run db:backup:pg` runs `pg_dump --format=custom`, prunes dumps older than
  `BACKUP_RETENTION_DAYS`, and never logs the password.
- `npm run db:restore:pg` refuses to run without `RESTORE_CONFIRM=RESTORE:<database>`; `--clean`
  additionally requires `RESTORE_ALLOW_DATA_LOSS=1`. Use `--dry-run` in drills.
- Backups must be encrypted with a KMS-managed key and stored outside the application host. See
  [`EXTERNAL-INFRA.md`](EXTERNAL-INFRA.md).

## 7. Verification

- `npx vitest run tests/data-lifecycle.test.ts` checks the seed guard, password handling, lifecycle
  fields in both schemas, and both initial migrations.
- Rehearse the full flow in a staging environment before each release: consent grant → outbound
  simulation → consent revoke → deletion request → anonymization → backup expiry.
